### 市場の既存「ポケカBOX価格比較表」の調査で見えた5つの欠点
国内の主要比較サイト・買取店価格表（どこたか、ポケカBOX比較、ポケソ、秋葉原系郵送買取各社）を横断調査した結果、既存価格表には以下の共通課題があることが分かった。

1. **「額面最高値」だけで実質手取りが見えない**
   - 送料条件（着払い条件・個数条件）、振込手数料（無料〜330円）、**価格保証ルール（申込時点／発送消印／到着日査定）**が別ページに散らばっており、額面で500円高い店へ送って送料や到着時値下がりで逆転するケースが多い。
2. **シュリンク無しの「ペナルティ幅（有無差額・差率）」が並べて見えない**
   - 抽選販売や家電量販店購入で「シュリンク無・ペリペリ有」の未開封BOXが増えているにもかかわらず、多くの比較表はシュリンク有りのみか、別画面に分断されている。
3. **「定価比（底値圏 vs プレミア帯）」と「店間差（相見積もり重要度）」が一目で分からない**
   - 同じ1,500円差でも、定価6,000円の新弾BOXと定価5,800円→45,000円の絶版BOXでは意味が異なる。公式定価に対する倍率と店間差率を並べることで、売却先選びの優先度が直感的に分かる。
4. **公開ページと個人比較表の法的・コンプライアンス境界が曖昧**
   - 他社買取価格表の店舗別生価格をそのまま公開Webへ転載すると、利用規約違反・不正競争・最新価格との乖離トラブルのリスクがある。
   - **個人用Googleスプレッドシート（非公開）**では店舗別比較・店舗条件比較をフル表示しつつ、**公開Web（GitHub Pages）やX/note発信素材**では店舗名を一切出さない**匿名統計インデックス**へ厳格分離する2層構造が最も安全かつ持続的。
5. **買取相場と「フリマ売却（メルカリ10%／Yahoo!フリマ5%）」が分断されている**
   - 実際の出品・売却判断では「買取店で即現金化」と「フリマで送料・手数料を払って売る」の手取り比較が不可欠。既存の無料ツール「トレカ損益ラボ」と1クリック連携させることで、相場確認→損益分岐点確認までを一気通貫にできる。

## 3. 再構築アーキテクチャ（2層公開モデル）

```
[6店舗の公開価格表（静的HTML×5 + Playwright×1）]
        │  PoliteRequester（アクセス間隔・リトライ制御）
        ▼
[正規化・名寄せ・カタログ付与（normalize.py / catalog.py / compare.py）]
  ・カートン／PSA／デッキセット除外
  ・74日分の既存推移アーカイブと100%互換の名寄せ別名辞書
  ・公式定価・シリーズ（MEGA / SV / スペシャルBOX / S&S / SM / XY・BW / 旧裏）付与
  ・最高値／中央値／最安値／2位価格／1位リード幅／店間差率を算出
        │
        ├──────────────────────────────┐
        ▼                              ▼
[個人用 Googleスプレッドシート]      [公開Web（GitHub Pages /market/）]
  ・店舗別価格比較（動的店舗列）        ・完全店舗匿名JSON（leak検査で物理ブロック）
  ・新タブ「シュリンク無比較」          ・参考高値／中央値／下限レンジ＋定価比
  ・新タブ「店舗条件」                  ・シュリンク無ペナルティ＆30日SVG推移
  ・74日+の推移アーカイブ継承           ・保有BOX資産計算モード（localStorage＋CSV）
  ・店舗匿名の「発信プロンプト」        ・トレカ損益ラボ（フリマvs買取）1クリック連携
```

## 4. 定期実行（GitHub Actions スケジュール遅延）に関する運用メモ

- GitHub Actions の `schedule: cron` は共有ランナー混雑により **指定時刻から数時間〜約10時間遅延**する現象が確認されている（`42 4 * * *` ＝ 13:42 JST 設定でも実開始が23時台になる日がある）。
- 本システムでは `manual-update.yml` に加えて、Vercelの手動更新ページからの即時 `workflow_dispatch` を併用可能。また、毎日定時に厳密実行したい場合は外部の軽量Cron（Vercel Cron や Cloudflare Workers Cron 等）から `workflow_dispatch` を叩く方式へ切り替えることで遅延を解消できる。
- 6店舗構成への拡張に伴い、`manual-update.yml` から `--strict` を外した。1店舗が一時的に取得失敗しても残り5店舗の最新価格でシートと公開インデックスを更新し、`更新履歴`（赤太字エラー件数）および `店舗条件`（赤字「未取得」）で異常を即座に検知できる設計としている。
